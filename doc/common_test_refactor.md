# Common Test parallelization report

## Scope

Baseline: `f1e8bf3bcbfe90c14433c093927e2ec953ade42e`.

The refactor changes scheduling in 17 Common Test suites and sizes three test-only domain caches for the concurrent workload. Production code, test bodies, scenario fixtures, assertions, expected events, retries, sleeps, timetraps, and test repetitions are unchanged. No tests were added, removed, or newly enabled. The existing unselected exports/groups remain unselected. The existing Common Test/CI entrypoint picks up the new groups automatically; no workflow or custom runner changes are required.

## Test-harness capacity

The first parallel trial exposed missing-party/missing-wallet failures in withdrawal setup. The DMT client fetches an object into its cache, queues cleanup, then wakes the waiting reader, which reads that cache entry. The former 10-entry Fistful and 20-entry Hellgate/party-management caches were too small for the simultaneous readers. Cleanup could evict a fetched object before the reader consumed it. Seven failures were recorded before the exploratory run was stopped; its timings are excluded from the benchmark.

The Fistful and Hellgate test helpers and `test/party-management/sys.config` now allow 1,000 entries. All retain the existing 50 MiB memory cap. The production `config/sys.config` is unchanged. No retry, timeout extension, mock, or assertion relaxation was added to hide these failures. Cache eviction is not an asserted scenario in these Common Test suites.

## Scheduling changes

- Enable `[parallel]` on the independent default groups in all five `ff_server` suites, the source, destination, deposit, transfer, withdrawal and withdrawal-adjustment suites, and the Fistful routing-rule suite.
- Keep withdrawal domain-revision changes and withdrawal-adjustment checks against shared provider balances behind serial boundaries.
- In withdrawal routing, run the first five independent cases together. Keep the cases that replace retryable-error application configuration serial.
- In the main invoice suite, add parallel child groups for independent payments, retries, captures, risk scores, refunds and chargebacks. Enable parallel holds, offsite preauthorization and ad hoc repairs. Keep the parent groups serial.
- Keep the main invoice suite's shared provider/system balance deltas, domain overrides, fault-detector settings, accumulated limit checks, adjustments and preprocessing mocks serial and in their original relative positions.
- In recurrent payments, parallelize customer-token cases between the existing cascade-domain changes. Preserve the cascade changes and their cleanup as serial boundaries.
- In templates, parallelize independent create/update cases between shared party/shop status mutations. Keep domain-changing terms retrieval last.
- In exchange tests, parallelize the final three failure cases, after the cashflow-changing adjustment. Each failure uses a separate currency shop.
- Preserve the existing parallel groups and the withdrawal-limits suite's `[sequence]` behavior.
- Keep terminal-affinity tests serial: their per-case cleanup resets shared domain objects, and several cases replace shared modules with mocks.

Only leaf groups run concurrently. A serial parent waits for a parallel child group to finish before starting the next mutation or balance check. This follows the [Common Test group execution rules](https://www.erlang.org/doc/apps/common_test/write_test_chapter.html#parallel-property-and-nested-groups).

The existing resource isolation is retained. Wallet/party IDs, invoice IDs, customer/card tokens and private shop accounts are generated by the same helpers as before. For example, the withdrawal-handler changed-body test reads a limit scoped to its own party despite the limit's historical `PAYTOOL` name. Cases asserting shared provider/system account deltas remain serial.

### Readability

Test bodies remain unchanged. Small, named child groups make concurrency boundaries visible in `groups/0`; no locking helpers, generic fixture remapping, or generated test bodies were introduced. Recursive group types describe nested definitions, and the template suite now exports `groups/0`. The original flattened case order is retained, although execution order within parallel groups is intentionally concurrent.

## Benchmarks

The original full run passed **420/420 cases**, with no failed or skipped cases. Its suite execution interval was **1,208 seconds (20m 08s)**. The main invoice suite accounted for **636 seconds (10m 36s)**.

The first completed refactored run passed **420/420 cases**, with no failed or skipped cases, in **674 seconds (11m 14s)**: **44.2% less suite execution time**, or **1.79× faster**. The main invoice suite fell to **323 seconds (5m 23s)**, a **49.2% reduction**.

The second full refactored run against fresh services also passed **420/420 cases**, with zero failures or skips, in **721 seconds (12m 01s)**: **40.3% less time**. Its main invoice suite took **329 seconds (5m 29s)**. Across the two refactored runs, the mean suite interval was **697.5 seconds (11m 37.5s)**, a **42.3% reduction** from the baseline. These are two repeat measurements, not a statistical confidence estimate.

### Environment and measurement method

- Docker Desktop on ARM64, configured with 8 CPUs and approximately 7.65 GiB of memory.
- Erlang/OTP 28.5.0, ERTS 16.4.0.6; Rebar 3.26.0.
- An isolated `paycore-ct-benchmark` Compose project uses the repository's pinned service images and tracing configuration. Host port publication is disabled in a temporary override to avoid conflicts with the developer's running project.
- Original suite sources were saved before editing and copied into `/tmp/paycore-ct-benchmark`. The refactored sources ran in the same checkout, with the same production sources, lockfile, toolchain and service images; the three documented test cache capacities are part of the refactor.
- Both variants execute `make common-test` (`rebar3 ct --cover`). No cases are filtered and coverage remains enabled. Each run starts a fresh Erlang VM. The installed Rebar 3.26 CT provider exports that VM's counters directly; the comparison imports only one run's `ct.coverdata` at a time, not an aggregate of previous runs.
- Execution times are extracted from Common Test's `suite.log` timestamps, from the first suite initialization to the last suite teardown, including suite/group setup and teardown and gaps between suites. Parallel case elapsed times are not summed to calculate wall time. Dependency downloads, compilation and Compose startup are separate setup costs.
- The baseline `make common-test` command took 1,485.054 seconds including first-use dependency restoration and compilation; the refactored commands took 716.400 and 743.357 seconds with dependencies already built. These command totals are not used to calculate the speedup.
- The user's reported 18-minute CI duration is contextual; these are local measurements, not a measured GitHub Actions result.

## Regression checks

The structural audit compares the original and refactored suite definitions and Erlang source tokens. It expands `all/0` and nested groups, compares the ordered list of selected cases including duplicates, checks that every selected case exports arity 1, and compares every function body except `all/0` and `groups/0`, ignoring whitespace and comments.

Structural result: all **420 selected cases across 21 suites** preserved; **968 functions defined in the suites** unchanged. Outside the suites, the two startup helpers change only the test cache capacity and its comment; the third cache setting is in the party-management test config. Parallel eligibility increases from **61 to 302 cases**. This verifies selection and source preservation; passing service-backed tests and coverage comparison are separate checks.

Baseline production coverage: **6,852 / 9,363 executable lines (73.182%) across 150 modules**, extracted from this run's `ct.coverdata`. Coverage is compared by `(module, source line)`, not just the overall percentage.

All three completed runs passed **420 cases with zero failures and zero skips**: 420 baseline executions and 840 refactored executions. Their actual runtime case inventories match, including repetition counts.

Neither refactored run lost any covered production lines. All three instrumented the same 150 modules and 9,363 executable lines.

## Interpretation and limits

The largest gains come from the invoice and withdrawal groups. Very short suites have little time to save and can be slightly slower due to scheduling/setup variation; all suite timings are shown above. Further parallelization of the remaining mutations and shared-balance assertions would require changing fixture ownership or rewriting the scenarios, so those cases retain their existing behavior and serial boundaries.

Coverage figures describe the repository modules instrumented by Rebar. They do not measure code inside separate service containers or dependency modules. Source preservation, identical executed case inventories, successful full runs and no lost production lines are the regression evidence here. Line coverage alone cannot prove every assertion retains the same fault-detection power; the unchanged scenario and assertion bodies are essential to that assessment.

### How the work unfolded

- The first native baseline attempt compiled successfully but could not run the service-backed cases while Docker was unavailable. The user started Docker; subsequent measurements used an isolated Compose project with fresh services for every full run.
- There were **three completed full runs**, totaling **1,260 passing case executions**: one original run and two refactored runs of the same 420 selected cases. Their measured suite intervals total **43m 23s**. The stopped exploratory cache-failure trial is additional and excluded from that total.
- The main implementation preserved test bodies and used named parallel groups with serial boundaries around shared-state changes. Parallel eligibility rose from 61 to 302 cases without adding a custom runner.
- The exploratory run exposed a test-cache capacity problem. The fix was confined to three test-only settings; both subsequent full runs passed without weakening assertions or extending timeouts.
- Purpose-built local audit scripts checked the ordered case selection and 968 unchanged suite functions, parsed Common Test timing logs, and compared covered source-line sets. The installed Rebar provider was inspected to confirm that coverage exports represented independent runs.
- Independent reads and checks were batched within tool calls. No work was delegated to subagents. One context compaction occurred during the task; the saved logs, source snapshots and audit artifacts carried the evidence through it.

A compact, task-scoped copy of the execution counters is retained at `/tmp/paycore-ct-evidence/execution-metadata.json`. The underlying sources are the original turn's `token_usage_record`, tool-call and lifecycle entries in the local Codex rollout, plus its turn-history duration. The log was scoped to the completed refactor turn so this appendix's own tool calls and token usage do not inflate the figures.
